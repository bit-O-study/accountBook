### 화면 원칙
- 화면마다 큰 숫자는 하나만.
- 거래 출처는 태그로 구분: `자동` `고정` `수동` `CSV` `카드대금` `이체`. 색과 글자를 함께 쓴다.
- 주요 기능은 홈에서 두 번 터치 안에 닿는다.
- 상태별 화면을 모두 만든다: 빈 상태, 불러오는 중, 부분 실패(배너), 전체 오류.

### 금액 표기
| 종류 | 표기 | 색 |
|------|------|----|
| 지출 | `-38,900` | `--minus` |
| 수입 | `+3,200,000` | `--plus` |
| 승인 취소 | `-12,000` 취소선 | `--faint` |

### 상태 색
| 상태 | 뜻 | 토큰 |
|------|----|------|
| `PAID` 납부완료 / `OK` 정상 | 문제없음 | `--good` |
| `SCHEDULED` 예정 / `SYNCING` 진행 | 기다리는 중 | `--accent` |
| `CHANGED` 금액변동 | 확인 필요 | `--warn` |
| `MISSING` 미확인 / `REAUTH` 재인증 / `ERROR` | 조치 필요 | `--bad` |

## 3. 자동 기록 (A)

### 처리 순서
```
수집 → 정리 → 중복 제거 → 종류 판정 → 분류 → 저장 → 고정지출 대조 → 반복 결제 감지 → 알림
```

| 단계 | 규칙 | 코드 |
|------|------|------|
| 수집 | 30분마다 + 앱을 열 때(5분 넘게 지난 계정만). 마지막 동기화 3일 전부터 겹쳐서 가져온다 | `sync/service.ts` |
| 정리 | 법인 표기 제거, 브랜드 사전으로 이름 통일 (“(주)우아한형제들” → 배달의민족) | `sync/normalize.ts` |
| 중복 제거 | ① 같은 계정·같은 외부 ID ② 자동끼리 같은 금액·가맹점·시각 ±10분 ③ CSV 와 자동 기록이 같은 날·금액·가맹점 ④ 수동/CSV 와 같은 날·금액·가맹점이면 하나로 합침 | `sync/dedupe.ts` |
| 종류 판정 | 은행 출금 중 “카드 + 결제/대금” → `CARD_BILL`. “내계좌/본인계좌” 또는 연결 계정 이름 포함 → `TRANSFER`. 나머지는 금액 부호로 `EXPENSE`/`INCOME` | `sync/categorize.ts` |
| 분류 | 내 규칙 → 가맹점 사전 → 업종코드(MCC) → 기타 | `sync/categorize.ts` |
| 취소 | 전체 취소는 원거래를 `CANCELED`, 부분 취소는 원거래 금액 조정 | `sync/service.ts` |

### 예외 정책
| 상황 | 처리 |
|------|------|
| 카드대금 출금 | 지출에서 제외 (카드 승인으로 이미 기록됨) |
| 내 계좌 간 이체 | “이체”로 표시, 통계 제외 |
| 할부 | 승인일에 총액 기록 (월 청구 기준 보기는 2단계) |
| 승인 취소 | 원거래 취소선, 합계 제외 |
| 부분 취소 | 원거래 금액 조정 |
| 해외 결제 | 승인 금액(원화) 기록, 매입 확정 보정은 실제 연동사 단계 |
| 환불 입금 | 수입으로 기록 (원거래 연결 제안은 2단계) |

### 연동사
- 인터페이스: `FinanceProvider.fetchTransactions(account, since, until)` (`sync/providers/types.ts`)
- 인증 실패는 `ProviderAuthError` → 계정 상태 `REAUTH`, 알림 발송. 그 외 오류는 `ERROR`, 2회 연속이면 알림.
- 1단계는 **데모 연동사**(`demo`)만 있다. 같은 날짜에 항상 같은 거래를 돌려줘 중복 제거를 검증할 수 있다. `providerConfig = "fail"` 이면 인증 실패를 흉내 낸다.
- 실제 연동사(CODEF 등)는 API 계약 후 같은 인터페이스로 추가한다.

### 동시 실행 (T12-fix1)
- 1단계의 단일 서버 프로세스 안에서 동일 계정의 동기화 요청이 겹치면 진행 중인 실행의 결과를 함께 기다린다. 수집·저장·상태 갱신은 한 번만 수행한다.
- 완료 또는 실패 후에는 다음 요청이 다시 실행될 수 있으며, 다른 계정의 수집은 막지 않는다. 개발 모드의 모듈 재로딩에도 실행 중 기록을 공유한다.
- 동기화 뒤 고정지출 대조·제안 알림은 사용자별로 순차 실행한다. 대조 도중 추가된 변경도 반영하도록 각 요청을 생략하지 않는다.
- 여러 서버 프로세스 간 잠금은 2단계 작업 큐 전환 범위다.

### CSV 가져오기
- 필수 열: 날짜, 가맹점, 금액. 선택: 시간, 승인번호. 카드사별 머리글 이름을 여러 개 받는다.
- 금액이 양수면 지출로 본다(카드 명세서 관례).
- 읽지 못한 줄은 빈 줄을 포함한 원본 줄 번호와 이유를 알려주고 정상 행만 저장한다. 금액은 0이 아닌 원 단위 정수이며 절댓값 2,147,483,647원 이내로 제한한다. 소수·지수 표기·문자 혼입·잘못된 쉼표는 재해석하거나 반올림하지 않는다.
- 시각이 비어 있으면 12:00을 쓰고 입력이 있으면 HH:mm 또는 HH:mm:ss의 유효 범위를 확인한다. 초는 기존 분 단위 기록에 맞춰 생략한다. 잘못된 날짜·시각·열 수·닫히지 않은 따옴표 행은 제외한다. 쉼표가 든 금액은 CSV 따옴표로 감싼다.
- 직접 입력의 지출/수입 방향은 선택한 종류로 정한다. 금액 칸은 부호 없는 정수(쉼표·원 접미사 허용)만 받으며 오류 시 내용·금액·메모·날짜·카테고리 초안을 유지한다.

## 4. 고정지출 (B)

### 등록
이름, 금액, 주기(매월·매주·매년), 결제일(매주는 요일), 카테고리, 결제수단, 대조용 이름, 알림(3일 전·1일 전 / 1일 전 / 당일 / 끄기), 종료일, 변동형(최소~최대 금액).

### 결제일 계산
- 31일 결제는 짧은 달에 말일로 보정 (2월 28일/29일, 4월 30일).
- 시작일 이전, 종료일 이후, 일시정지 중에는 회차를 만들지 않는다.

### 납부 대조
| 기준 | 값 |
|------|----|
| 날짜 허용 범위 | 결제일 ±3일 |
| 금액 허용 범위 | ±10% (변동형은 최소~최대) |
| 같은 거래 | 한 거래는 한 회차에만 연결 |

```
예정 ──(맞는 거래 발견)──▶ 납부완료
     ──(금액 10% 넘게 차이)──▶ 금액변동
     ──(결제일 +3일 지나도 없음)──▶ 미확인
```
여러 후보가 있으면 금액이 맞는 것, 그다음 결제일에 가까운 것을 고른다.

### 반복 결제 감지 (등록 제안)
| 주기 | 최소 횟수 | 간격 | 살펴보는 기간 | 끊김 판정 |
|------|----------|------|--------------|----------|
| 매월 | 3회 | 25~35일 | 125일 | 마지막 결제 후 38일 |
| 매주 | 4회 | 6~8일 | 45일 | 마지막 결제 후 10일 |

- 금액은 중앙값 ±10% 안.
- 기간 안의 거래가 **모두** 규칙적이어야 한다 (매일 가는 카페는 제외).
- 이미 등록된 가맹점, “무시”한 가맹점(90일)은 제외.
- 자동 등록하지 않고 **제안만** 한다.

## 5. 예산 (C)

- 생활비 예산 = 고정지출을 **뺀** 월 예산. 고정지출로 연결된 거래는 생활비에 안 센다.
- 예산은 월별로 저장하고, 그 달 예산이 없으면 가장 최근 달 예산을 쓴다.

| 값 | 계산 |
|----|------|
| 생활비 사용 | 이번 달 지출 − 고정지출 납부액 |
| 예산 남음 | 예산 − 생활비 사용 |
| 하루 가능 금액 | 예산 남음 ÷ 남은 날짜(오늘 포함), 0 미만이면 0 |
| 예산 속도 | 예산 × 오늘까지 일수 ÷ 그 달 일수 |
| 남은 고정지출 | 이번 달 `예정` + `미확인` 회차 금액 |
| 월말 예상 잔액 | 수입 − 지출 − 남은 고정지출 − max(0, 예산 남음) |

지출 합계에 들어가는 거래: `EXPENSE` · `APPROVED` · 통계 제외 아님.

## 6. 알림

| 종류 | 시점 | 문구 예 |
|------|------|---------|
| `DUE` 결제 예정 | 알림 설정 일수 (기본 D-3, D-1) | 내일 월세 550,000원이 나가요. |
| `CHANGED` 금액 변동 | 대조 시 | SKT 통신요금이 59,000 → 71,500원으로 바뀌었어요. |
| `MISSING` 납부 미확인 | 결제일 +3일 지남 | 실손보험 84,000원이 아직 안 나갔어요. |
| `SUGGEST` 새 고정지출 | 감지 시 | 유튜브 프리미엄 14,900원이 3번 반복 결제됐어요. |
| `SYNC_FAIL` 연동 끊김 | 인증 실패 또는 2회 연속 실패 | 현대카드 내역을 가져오지 못했어요. |

- 같은 알림은 `key` 로 한 번만 만든다.
- 1단계는 앱 안 알림만. 웹 푸시·이메일, 방해 금지(22:00~08:00), 하루 3건 묶음은 2단계.

## 7. 데이터 모델

`prisma/schema.prisma` 참고. 요점:

- `Transaction.amount`: 원 단위 정수, 지출 음수.
- `Transaction.kind`: `EXPENSE | INCOME | TRANSFER | CARD_BILL`
- `Transaction.source`: `AUTO | MANUAL | CSV`
- `(accountId, externalId)` 유니크 → 같은 거래가 두 번 들어오지 않는다.
- `RecurringOccurrence`: 규칙 × 결제일 하나. `transactionId` 유니크 (한 거래는 한 회차).
- 날짜 문자열(`startDate`, `dueDate` 등)은 KST `YYYY-MM-DD`, 시각(`occurredAt`)은 UTC.

## 9. 로그인·회원가입 (P2-03)

- 금융 연동 계약 없이 진행하는 첫 2단계 작업이다. 이메일을 로그인 ID로 사용하고 이름·비밀번호로 가입한다. 이메일은 앞뒤 공백 제거·소문자로 통일하며 비밀번호는 15~128자, 공백을 포함한 입력 그대로 처리한다.
- `/login`, `/signup`을 공개한다. 가계부 화면과 모든 서버 액션은 DB 세션으로 확인한 사용자만 접근한다. 신규 가입자는 빈 가계부에서 시작하며 공통 카테고리는 유지한다.
- Node 내장 scrypt(N=32768, r=8, p=3)와 무작위 salt로 비밀번호를 해시한다. 32바이트 무작위 세션 토큰의 SHA-256만 DB에 저장하고 원본은 HttpOnly·SameSite=Lax·Path=/ 쿠키로 전달한다. 운영 쿠키는 Secure, 세션 만료는 7일이며 로그아웃하면 DB 세션을 폐기한다.
- 인증 요청은 이메일별 15분에 10회, 서버 전체 분당 100회로 제한한다. 실패 응답은 이메일 존재 여부를 구분하지 않는다.
- 기존 사용자의 이메일·비밀번호는 비어 있는 상태로 보존한다. 서버 관리자가 사용자 ID를 명시해 30분짜리 일회용 연결 코드를 발급하면 가입 화면에서 그 가계부에 로그인 정보를 연결할 수 있다. 공개 웹 화면에서는 연결 코드를 발급하거나 기존 사용자 목록을 조회할 수 없다.
- 거래·규칙·계정·예산·알림은 로그인 사용자 기준으로 분리한다. 알림 중복 키는 사용자와 키의 조합으로 제한한다. 백그라운드 동기화는 요청 쿠키에 의존하지 않는다.
- 이번 범위는 로컬 이메일/비밀번호 인증이다. 이메일 소유 확인, 이메일을 통한 비밀번호 재설정, 소셜 로그인은 포함하지 않는다.
- 비밀번호 해시 기준: [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). 세션·서버 액션 확인 기준: [Next.js 인증 가이드](https://nextjs.org/docs/app/guides/authentication).

## 10. PostgreSQL 전환 (P2-04)

- `prisma/schema.prisma`의 모델을 정본으로 두고 provider와 클라이언트 출력 경로만 바꿔 PostgreSQL 및 이전용 스키마를 생성한다.
- 이전 시 앱·자동 동기화를 중지하고 SQLite 백업을 확보한다. 원본은 읽기만 수행하며 모든 모델의 ID·관계·날짜·금액·인증 정보를 보존한다.
- 대상 PostgreSQL의 앱 테이블이 모두 비어 있을 때만 이전한다. 대상 테이블 잠금, 삽입, 전체 행·열 해시 비교를 한 트랜잭션 안에서 수행한다. 오류나 불일치가 있으면 전부 롤백한다. 기존 대상 데이터의 삭제·덮어쓰기는 제공하지 않는다.
- 실제 PostgreSQL에서 데이터·제약·앱 동작을 검증한다. 로컬 검증 완료와 운영 접속 정보로 실제 전환한 상태를 구분한다. 외부 운영 DB 정보가 없는 동안 기본 실행은 기존 SQLite를 유지한다.

## 11. NestJS API 분리 (P2-05)

- Next.js는 화면·쿠키·서버 액션을 담당하고 NestJS 별도 프로세스는 인증·조회·저장·동기화를 담당한다. 기존 비즈니스 규칙은 공통 서비스로 추출하여 양쪽 실행 방식에서 공유한다.
- `ACCOUNTBOOK_API_URL`이 설정되면 Next 서버가 API로 요청한다. 미설정 시 기존 단일 프로세스 모드를 유지한다. API 오류가 발생해도 로컬 DB로 자동 우회하지 않는다.
- API는 서버 간 전용이다. `ACCOUNTBOOK_API_KEY`(최소 32자)로 호출 서버를 확인하고, 사용자 요청은 기존 DB 세션 토큰을 Bearer로 전달하여 매번 확인한다. 요청 본문의 사용자 ID를 신뢰하지 않고 세션에서 사용자 ID를 결정한다. API는 기본적으로 loopback에 바인딩하고 CORS를 열지 않는다.
- 브라우저 쿠키는 기존 HttpOnly·SameSite·Secure 정책을 유지한다. 브라우저는 Next 서버 액션으로 저장하며 기존 동일 출처 검사를 유지한다. API 세션 토큰 응답은 서버에서만 처리하고 화면에는 전달하지 않는다.
- `/v1/auth/:operation`, `/v1/queries/:operation`, `/v1/commands/:operation`은 명시적으로 허용한 작업만 제공한다. 필드 형식과 본문 크기를 제한하고, 조회 결과의 Date는 명시적인 전송 형식으로 복원한다. DB 오류나 내부 접속 정보는 응답하지 않는다.
- API 모드에서는 Next의 30분 타이머를 끄고 API 프로세스만 동기화한다. 여러 API 인스턴스 지원은 P2-06의 작업 큐 범위다.
- 원본 DB를 보존하고 별도 테스트 DB에서 단일 프로세스와 API 모드의 데이터·화면·접근 제한을 비교한다.

## 12. Redis + BullMQ 동기화 (P2-06)

- `SYNC_MODE=queue`와 `REDIS_URL`로 큐 모드를 선택한다. 미설정 시 기존 로컬 모드를 유지한다. 큐 모드는 별도 워커가 처리하며 Next/API 내부의 주기 타이머를 중지한다. Redis나 워커 장애 시 동기화를 로컬에서 중복 실행하지 않는다.
- BullMQ Job Scheduler의 고정 ID로 기본 30분마다 사용자별 동기화 작업을 등록한다. 수동 동기화·새 연결·재연결·앱 열 때의 5분 경과 확인도 같은 큐를 사용한다. 실행 직전에 소유권·계정 존재·재인증·최근 동기화 시각을 다시 확인한다.
- 사용자 ID의 해시로 고정된 8개 큐 중 하나를 선택하고 각 큐의 전역 동시 실행 수를 1로 둔다. 여러 워커가 떠도 같은 사용자의 계정 수집과 후처리는 순서대로 실행한다. 다른 큐의 사용자는 병렬 처리하며 같은 큐에 배정된 사용자는 대기할 수 있다.
- 동일한 종류·대상·옵션의 진행 중 동기화 요청은 하나로 합친다. 데이터 변경 후 대조 작업은 생략하지 않는다. 큐에는 사용자/계정 ID와 옵션만 저장하고 금융 인증정보나 거래 원문을 넣지 않는다.
- 일시적 실패는 최초 실행을 포함해 최대 3회, 기본 1초에서 시작하는 지수 간격으로 재시도한다. 재인증이 필요한 실패는 자동 재시도하지 않는다. 실패 사용자 때문에 다른 사용자 작업이 중단되지 않는다. 종료 시 새 작업 수락을 멈추고 진행 중 작업을 마친다. 비정상 종료 작업은 BullMQ의 stalled 복구로 다시 처리될 수 있다.
- 큐 전달은 최소 1회 처리 방식이다. 취소 기록과 원거래 금액 변경을 같은 DB 트랜잭션으로 묶고 외부 거래 ID로 재처리를 판별하여 재시도 중 부분취소가 중복 반영되지 않게 한다. 자동 거래 고유 제약 충돌은 중복으로 처리한다.
- 화면 요청은 최대 90초까지 결과를 기다린다. 대기 시간 초과는 작업 취소가 아니며 오류 안내 뒤에도 큐의 작업은 남는다. 성공 작업은 최대 1시간/5,000개, 실패 작업은 24시간/5,000개까지 보존한다. Redis 영속화와 noeviction을 운영 전제로 한다.
- 이번 범위는 동기화와 변경 후 대조의 큐다. 모든 사용자 편집을 분산 트랜잭션으로 바꾸거나 네트워크 분할에서 정확히 한 번 실행을 보장하는 작업은 포함하지 않는다. 별도 DB·Redis로 중복 등록, 여러 워커, 재시도, 중단 복구와 실제 화면을 검증한다.

## 13. 외부 알림 (P2-07)

- 앱 안 알림은 기존대로 즉시 저장한다. 외부 알림은 기본 꺼짐이며 사용자가 `/notifications`에서 채널별로 켠다. 켜기 전 알림과 묶음 생성 시 이미 읽은 알림은 제외한다.
- 한국시간 08시·13시·19시에 새 미확인 알림을 묶어 사용자당 하루 최대 3개 묶음을 만든다. 한 묶음은 동의한 이메일 및 구독 브라우저로 각각 전달한다. 알림이 없으면 보내지 않는다. 22:00~08:00에는 시작하지 않으며, 중단 후에는 현재 시간대만 처리하고 과거 시간대를 연달아 발송하지 않는다. 실제 수신 시각은 공급자·기기 상태에 따라 늦어질 수 있다.
- 외부 내용은 새 알림 건수와 로그인 후 알림 화면으로 연결하는 안내만 포함한다. 금액·거래처·금융 인증정보는 포함하지 않는다. 기존 앱 알림을 읽음으로 바꾸지 않는다.
- 이메일은 로그인 이메일만 사용하며 10분 유효 6자리 확인 코드로 소유 확인 후 켠다. 확인 요청은 1분 간격, 15분에 3회, 코드 입력은 최대 5회다. 확인 메일은 사용자가 요청한 인증 메일이므로 묶음·방해 금지 예외다. 외부 전송 설정이 없으면 켤 수 없다.
- 푸시는 사용자의 버튼 동작으로만 브라우저 권한을 요청한다. 구독은 사용자별로 최대 5개이고 해제는 소유자만 가능하다. 알려진 브라우저 푸시 서비스의 HTTPS 주소만 받아 임의 서버로의 발송을 차단한다. 만료(404/410) 구독은 삭제한다. 알림 클릭은 고정된 동일 출처 `/notifications`로만 이동한다.
- 별도 알림 워커가 1분마다 DB를 확인한다. 사용자/시간대 묶음의 고유 제약과 발송 상태의 조건부 변경으로 여러 워커의 중복 처리를 막는다. 성공 건은 재발송하지 않는다. 명백한 일시 거절은 같은 시간대 안에서 최대 3회 재시도한다. 연결 단절·타임아웃처럼 수락 여부가 불확실하거나 발송 중 중단된 건은 `UNKNOWN`으로 기록하고 자동 재발송하지 않는다. 누락 가능성과 정확히 한 번 보장의 한계를 운영 문서에 명시한다.
- 채널을 끄거나 구독을 해제하면 대기 발송을 취소한다. 이미 전송 중인 건은 회수할 수 없다. SMTP·VAPID 설정 및 `NOTIFICATION_DELIVERY=enabled`는 서버 운영자가 설정한다. 이번 개발 검증은 격리 DB·가짜 전송기·SMTP/푸시 어댑터 모킹으로 수행하고 실제 외부 수신자에게 발송하지 않는다. 기존 로컬 DB는 일관된 백업을 만든 뒤 복제본에서 새 테이블 추가와 기존 12개 모델의 전체 데이터 해시 보존을 확인하고 적용한다. 실제 외부 서비스·운영 DB 검증은 별도 절차로 제공한다.

## 14. 할부 월별 예상 청구 (P2-08)

- 거래 상세에서 지출 거래에 2~60개월과 첫 청구 월을 직접 지정한다. 첫 청구 월은 승인 월 이후(같은 월 포함)여야 한다. 1개월은 일시불로 되돌린다. 실제 카드사 청구일·이자·수수료는 추정하지 않는다.
- 승인 거래의 금액·일자와 기존 대시보드·예산·거래 통계는 그대로 유지한다. 별도 `/installments` 화면은 선택한 달에 배분되는 할부 원금만 합산하며 일시불·카드대금 출금은 포함하지 않는다.
- 저장 전 전체 회차별 예상 원금과 기간을 미리 보여 준다. 월별 조회에는 선택 회차 이후의 남은 원금(해당 회차 제외)을 함께 표시한다. 납부 완료나 실제 카드 잔액으로 해석하지 않는다.
- 원금은 원 단위로 균등 분할하고 나머지 1원은 앞 회차부터 배분한다. 총 회차 합은 현재 거래 금액의 절댓값과 일치한다. 월말 날짜와 무관하게 첫 청구 월에서 한 달씩 이동한다.
- 취소·통계 제외·수입·이체·카드대금 거래는 예상 합계에서 제외한다. 부분취소로 원금이 바뀌면 전체 회차를 현재 원금으로 다시 계산하므로 과거 예상액도 달라질 수 있다. 이는 실제 납부 이력이나 카드 명세서가 아니다.
- 사용자 세션 소유권을 저장·조회 양쪽에서 검사하며 로컬/API 모드에서 같은 서비스를 사용한다. 미래 월도 조회할 수 있다. 기존 DB에는 기본값 1개월과 nullable 첫 청구 월만 추가한다.

## 15. 환불 원거래 연결 (P2-10)

- 환불은 기존대로 수입으로 기록한다. 연결은 설명을 위한 표시이며 원거래 지출·환불 수입·예산·할부 원금을 상계하거나 수정하지 않는다. 자동 연결하지 않고 사용자가 후보를 확인한 후 확정한다.
- 환불 연결 화면은 조회 월의 승인된 양수 수입을 보여 준다. 미연결 수입에는 같은 정규화 가맹점의 지출 중 환불일 이전 180일 이내(같은 날 포함), 승인 상태이며 통계 제외가 아니고 미연결 잔여 원금이 환불액 이상인 거래를 최대 5개 제안한다. 금액이 정확히 남는 후보, 날짜가 가까운 후보 순이다. 동명 가맹점·일반 입금일 수 있으므로 제안만으로 환불 여부를 확정하지 않는다.
- 환불 1건은 원거래 1건에 연결한다. 원거래에는 여러 부분 환불을 연결할 수 있지만 연결 시 합계가 원금을 넘을 수 없다. 저장 시 소유권·종류·승인·날짜·가맹점·금액을 다시 검사하고 경쟁 저장은 직렬화/재시도한다.
- 사용자가 연결을 해제할 수 있다. 환불/원거래 삭제 시 참조만 없애며 다른 거래를 삭제하지 않는다. 연결 뒤 원거래 취소·금액 수정·통계 제외가 발생해도 기록을 자동 변환하지 않고 현재 거래 상태를 확인하라는 안내를 표시한다. 연결 금액은 해당 환불 거래의 현재 금액이다.
- 기존 DB에는 nullable 원거래 참조와 인덱스를 추가한다. 사용자별 조회/변경과 로컬/API 양쪽을 검증하고 기존 모든 금액·집계 보존을 확인한다.

### 거래 상세 바로 열기 (P2-10-followup1)

- /transactions?tx=거래ID는 세션 소유자의 단건을 별도 조회해 상세 창으로 연다. 현재 목록의 월/검색/필터와 무관하며 목록 합계에는 추가하지 않는다. 없는 ID와 타인 ID는 같은 안내를 보여 준다.
- 상세에 연결된 원거래와 환불 목록을 표시하며 링크는 현재 목록 조건을 유지하고 tx만 바꾼다. 할부/환불 화면의 원거래 링크도 해당 거래를 직접 연다. 사용자 이름·금융 인증정보 등 불필요한 데이터는 조회하지 않는다.
- 목록에서 열기와 연결 거래로 이동은 브라우저 방문 기록에 남긴다. 닫기는 현재 URL의 tx만 제거하고 목록 월/검색/필터를 보존한다. 브라우저 뒤로/앞으로 이동하면 URL에 따라 상세가 복원된다. 대시보드 거래를 열 때도 해당 월 거래내역의 같은 상세로 이동한다.
