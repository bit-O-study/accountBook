# 가계부 서비스 설계 보완 검토

| 항목 | 내용 |
| --- | --- |
| 대상 문서 | AB-DR-001 v0.3 |
| 문서 성격 | v0.4 개정을 위한 분석 및 수정 제안 |
| 작성일 | 2026-10-23 |
| 검토 근거 | 대화로 전달된 기능 기획, 화면 설계, 거래 처리 및 고정지출 규칙 |
| 상태 | 제안 초안 — 제품 정책 확정 및 승인 전 |

> 이 문서는 설계 검토 결과이며 구현 완료 보고서가 아니다. 아래 권장안을 기존 확정 요구사항과 구분한다. 대화에서 세부 내용이 확인되지 않은 항목은 전체 원문에도 없다고 단정하지 않고 확인·보완 대상으로 취급한다.

## 1. 검토 결론

가장 큰 문제는 기능 수의 부족이 아니라 **동일한 거래를 지출·예산·고정지출·잔액에서 해석하는 기준이 아직 통일되지 않았다는 점**이다.

v0.3은 화면 구성과 사용 시나리오를 논의하기에는 충분하지만, 금액 계산과 자동 판정을 그대로 구현할 명세로는 보완이 필요하다. 금융 API 계약과 인증정보 보관 방식 외에도 다음 정책을 확정해야 한다.

1. 소비 집계와 계좌 현금흐름의 구분.
2. 생활비 예산 및 월말 예상 금액의 정의.
3. 고정지출 등록·수정 시 과거 거래와 예산에 적용하는 범위.
4. 거래 중복·갱신·취소·환불의 연결 규칙.
5. 납부 확인, 금액 변동, 데이터 수집 상태의 구분.
6. 데이터 누락 시 통계·비교·예측의 표시 기준.

v0.4에서는 기능 추가보다 **거래 처리 규칙표, 금액 계산표, 고정지출 상태 전환표**를 우선 확정한다.

## 2. 금액의 의미와 계산 기준

### 2.1 현재 화면의 숫자는 서로 다른 의미를 가진다

| 화면 숫자 | 의미 | 보완점 |
| --- | --- | --- |
| 이번 달 지출 1,284,500원 | 현재까지 기록된 소비 | 취소·환불·이체·누락 처리 기준 필요 |
| 생활비 예산 남음 375,500원 | 설정한 생활비 예산 중 미사용액 | 고정지출 분류 변경 시 재계산 정책 필요 |
| 남은 고정지출 620,000원 | 앞으로 결제될 것으로 예상되는 금액 | 납부 확인 여부와 금액 변동 반영 필요 |
| 월말 예상 잔액 920,000원 | 현재 명세에서 산식이 명시되지 않은 예상값 | 실제 계좌 잔액인지 소득 잉여액인지 구분 필요 |

예시의 920,000원은 다음 산식과 일치한다.

```text
월수입 3,200,000 - 생활비 예산 1,500,000 - 월 고정지출 780,000
= 920,000원
```

이 산식을 의도했다면 이는 **예산을 지켰을 때 이번 달 소득에서 남는 금액**이다. 월초 잔액, 급여 입금일, 카드 청구일 등을 고려한 실제 통장 잔액 예측은 아니다.

### 2.2 1차 제품의 권장 표현

| 기존 표현 | 권장 표현 | 이유 |
| --- | --- | --- |
| 하루 가능액 | 하루 생활비 예산 | 실제 지급 능력으로 오해하지 않도록 함 |
| 월말 예상 잔액 | 예산 준수 시 남는 소득 | 계산 결과의 의미를 명확히 함 |

실제 계좌 잔액 예측은 기초 잔액·예정 입출금·카드 청구일을 다루는 별도 기능으로 둔다. 수입이 미입력된 경우와 실제 수입이 0원인 경우도 구분한다.

### 2.3 예시 산식 검증

| 지표 | 산식 | 결과 |
| --- | --- | --- |
| 생활비 지출 | 1,284,500 - 160,000 | 1,124,500원 |
| 남은 생활비 예산 | 1,500,000 - 1,124,500 | 375,500원 |
| 하루 생활비 예산 | 375,500 ÷ 9일 | 원 미만 버림 시 41,722원 |
| 예산 진행선 대비 초과 | 1,124,500 - (1,500,000 × 23 ÷ 31) | 원 단위 반올림 시 11,597원 |
| 월 고정지출 | 160,000 + 620,000 | 780,000원 |

**‘예산 속도보다 11,597원 많이 씀’은 올바른 계산이다.** 앞선 대화에서 계산 오류 가능성을 지적한 내용은 정정한다.

하루 예산은 10월 23일 기준 오늘을 포함한 9일로 계산한 예시다. 다음 정책을 명시해야 한다.

- 오늘 포함 여부와 원 단위 반올림·버림 방식.
- 예산 초과 시 하루 예산은 0원으로 표시하고 초과액을 별도 안내할지 여부.
- 과거 월·미래 월에서 하루 예산을 표시하는 방식.
- 예산 미설정과 예산 0원의 구분.
- 월 중간 예산 변경 시 과거 알림과 현재 계산의 처리.

## 3. 소비 집계와 현금흐름 분리

카드 승인일에 소비를 기록하고 카드대금 출금을 소비에서 제외하는 방식은 소비 분석의 기준이다. 이를 계좌 잔액 예측에도 그대로 적용하면 잘못된 결과가 나온다.

```text
10월 카드 사용 300,000원 → 10월 소비에 포함
11월 카드대금 출금 300,000원 → 11월 소비에는 제외, 계좌 현금흐름에는 포함
```

| 거래 유형 | 소비 통계 | 계좌 현금흐름 |
| --- | --- | --- |
| 카드 승인 | 포함 | 승인 시점에는 은행 계좌 출금 없음 |
| 카드대금 납부 | 제외 | 해당 계좌 출금으로 포함 |
| 내 계좌 간 이체 | 제외 | 각 계좌에는 반영, 추적 대상 양쪽 계좌를 합산하면 상쇄 |

### 권장 규칙

- 거래 유형과 집계 기준을 분리한다. 하나의 `제외` 설정으로 모든 통계에서 제거하지 않는다.
- 카드 상세내역이 없더라도 카드대금을 임의로 소비에 포함시키지 않는다. 상세내역을 나중에 가져오면 중복될 수 있다.
- 카드 상세내역이 없는 기간은 소비 집계가 불완전함을 표시한다.
- 본인 계좌 이체는 연결 계좌 정보 또는 사용자 확인으로 판정한다. 거래명 문구만으로 확정하지 않는다.
- 승인 기준과 청구 기준 리포트는 기준을 명확히 표시하고 합계를 혼합하지 않는다.

## 4. 고정지출 등록과 예산의 상호 영향

생활비 예산에서 고정지출을 제외한다면, 반복 결제를 고정지출로 등록하는 행동은 예산 계산 기준까지 변경한다.

### 문제 사례

유튜브 14,900원이 생활비로 집계된 뒤 고정지출로 등록되면 다음 변화가 발생할 수 있다.

1. 과거 거래까지 연결하면 생활비 사용액이 줄어든다.
2. 생활비 잔여 예산과 하루 예산이 늘어난다.
3. 이전에 발송한 예산 초과 알림과 현재 화면이 달라진다.
4. 과거 월 리포트가 바뀔 수 있다.

### 권장 규칙

- 등록 시 적용 시작 회차와 기존 거래 연결 여부를 지정한다.
- 저장 전에 이번 달 생활비 집계에 미치는 영향을 보여준다.
- 기본적으로 과거 마감 월을 유지하고 선택한 시작 회차부터 적용한다. 마감의 의미와 수정 허용 정책은 별도 확정한다.
- 과거 거래 변경은 명시적으로 선택하게 한다.
- 규칙 수정은 ‘이번 회차만’과 ‘이후 회차부터’를 구분한다.
- 일시정지·종료가 이미 확인된 과거 납부 기록을 바꾸지 않도록 한다.
- 예상 금액은 실제 거래와 별도로 보관하며, 예상 회차를 생성했다는 이유만으로 실제 지출을 추가하지 않는다.

**검수 불변 조건:** 고정지출 등록 전후에 전체 소비 금액은 같아야 한다. 생활비와 고정지출 간 구성만 바뀐다.

## 5. 납부 상태를 세 가지 판단으로 분리

현재 ‘예정·납부완료·금액변동·미확인’은 서로 다른 성격의 상태를 한 목록에 섞고 있다. 금액이 달라도 납부는 완료될 수 있고, 연동이 끊겨도 실제 납부는 이루어졌을 수 있다.

| 판단 축 | 예시 상태 |
| --- | --- |
| 납부 확인 | 예정 / 납부 확인 / 기한 경과 미확인 |
| 금액 비교 | 정상 범위 / 금액 변동 / 비교 불가 |
| 데이터 수집 | 최신 / 수집 지연 / 연결 끊김 / 범위 확인 불가 |

화면에서는 다음과 같이 조합한다.

- `납부완료 · 예상보다 12,500원 많음`
- `연동 지연 · 납부 여부 확인 불가`

거래를 찾지 못한 사실을 미납으로 단정하지 않는다. 현금이나 다른 계좌로 납부했을 수 있으므로 **‘납부 미확인’** 표현을 유지한다.

### 알림 시점 충돌

| 항목 | 충돌하는 내용 | 권장 정리 |
| --- | --- | --- |
| 결제 예정 | D-1 / D-3·D-1 | 기본 D-1 09:00, D-3 선택 제공 등 단일 정책 확정 |
| 납부 미확인 | D+3 09:00 / `today > due + 3` | ±3일 전체를 대조한다면 D+3 종료 후 판정하고 수집 상태도 확인 |
| 금액 변동 | 10% 증가 / 증가·감소 모두 | 예상액 대비 절대 차이가 10% 초과일 때 변동 |

단순히 D+4로 시간을 늦추는 것만으로는 충분하지 않다. 해당 대조 기간의 거래 수집 상태가 불확실하면 확인 불가로 표시한다. 제공기관이 수집 완전성을 보장하지 않는다면 앱도 완전 수집을 확정해서 표시하지 않는다.

## 6. 반복 감지와 납부 대조의 기준 분리

| 기능 | 오탐의 영향 | 권장 방향 |
| --- | --- | --- |
| 반복 결제 감지 | 불필요한 등록 제안 | 근거를 보여주고 등록·무시 선택 제공 |
| 납부 자동 대조 | 실제로 납부하지 않은 항목을 완료로 표시 | 더 보수적으로 판정하고 애매한 후보는 확인 요청 |

### 가맹점·날짜만으로 구분하기 어려운 사례

- 같은 통신사의 본인·가족 요금.
- 같은 서비스의 정기 구독과 추가 구매.
- 같은 보험사의 여러 보험료.

### 권장 대조 순서

1. 결제 계정·가맹점·날짜·금액 등의 근거로 해당 회차의 결제인지 판단한다.
2. 연결할 근거가 충분한 경우 예상 금액과 비교한다.
3. 후보가 여러 개이거나 근거가 부족하면 사용자 확인을 요청한다.

금액 ±10%를 거래 탐색의 필수 조건으로 사용하면 안 된다. 예를 들어 59,000원이 71,500원으로 오른 결제를 탐색 단계에서 제외하면 금액변동이 아니라 미확인으로 오판할 수 있다.

### 추가 확정 사항

- 정상 범위 경계는 정확히 10%까지 포함할지 명시한다.
- 전기·가스 등 변동형 지출은 예상 범위 또는 최근 평균 등 별도 정책을 둔다.
- 월간·주간·연간 반복 감지에 필요한 관측 횟수와 허용 오차를 구분한다.
- 31일 결제의 말일 보정, 윤년, 휴일 이동을 정의한다.
- 무시 후 90일 재제안 금지의 식별 기준을 정한다. 동일 브랜드의 다른 구독까지 일괄 차단되지 않도록 한다.
- 자동 연결 해제·거래 재선택·수동 납부 확인을 제공한다.
- 수동 납부 확인 뒤 실제 거래가 들어와도 소비를 두 번 추가하지 않는다.

## 7. 중복 제거를 넘어 거래의 변화 추적

거래는 다음 순서로 여러 번 들어오거나 변경될 수 있다.

```text
수동 입력 → CSV 업로드 → 자동 연동 → 매입 금액 확정 → 부분 취소
```

각각을 새 거래로 저장하면 중복되고, 유사하다는 이유로 삭제하면 정상 결제가 사라진다.

### 권장 원칙

- 기관·계정·외부 거래 ID 등 안정적인 식별 정보를 우선한다.
- 원본 기록과 사용자에게 보여줄 거래의 연결 관계를 보존한다.
- 취소·환불을 원거래와 연결하고 같은 이벤트는 한 번만 반영한다.
- 사용자 메모·카테고리·집계 설정을 재수집으로 덮어쓰지 않는다.
- 불확실한 중복은 후보로 제시하고 연결을 되돌릴 수 있게 한다.
- 표시용 가맹점명 정규화와 거래 식별을 구분한다. 같은 브랜드로 표시해도 원본 매장·결제 정보는 보존한다.

‘금액·시각 ±10분·가맹점 일치’는 중복 후보를 찾는 근거일 뿐이다. 같은 매장에서 같은 금액을 연속 결제하는 정상 사례가 있으므로 확정 삭제 기준으로 사용하지 않는다.

### CSV 보완 항목

- 지원 양식과 인코딩, 날짜·금액 형식.
- 오류 행과 정상 행을 함께 발견했을 때 저장 정책.
- 저장 전 미리보기와 중복 후보 확인.
- 같은 파일 재업로드 시 중복 생성 방지.
- 수동·CSV·자동 거래 간 연결 정책.

### 취소·환불 보완 항목

- 원거래 금액을 덮어쓰기만 하지 않고 조정 이력을 보존한다.
- 지난달 결제의 이번 달 환불을 어느 달 통계에 반영할지 정한다.
- 고정지출에 연결된 거래가 취소되면 납부 상태를 재평가한다.
- 부분 취소를 여러 번 수집해도 같은 금액이 반복 차감되지 않아야 한다.

## 8. 데이터 완전성을 화면에 반영

‘3분 전 동기화’는 조회를 실행한 시점일 뿐 거래가 완전하고 최신이라는 보장은 아니다.

구분할 정보는 다음과 같다.

- 마지막 조회 시도 시각.
- 마지막 성공 시각.
- 확인 가능한 조회 범위.
- 실패하거나 지연 중인 기관.

### 잘못된 해석 사례

현대카드 내역이 4일 비어 있는 동안 ‘전월 대비 지출 8.2% 감소’를 강조하면 사용자가 데이터 누락을 절약 성과로 오해할 수 있다.

### 권장 화면 정책

- 합계 옆에 `일부 내역 미반영`을 표시한다.
- 증감률·예측값에도 동일한 데이터 한계를 표시하거나 계산 보류 기준을 적용한다.
- 상단 오류 배너만으로 숫자 자체의 불완전성을 대신하지 않는다.
- 재연결 뒤 누락 기간을 채운 후 관련 통계와 납부 상태를 재평가한다.
- 동기화 실패 시 마지막 성공 데이터는 유지한다.

## 9. 연동·알림·운영 보완

### 9.1 동기화 약속

‘30분마다 조회’와 ‘결제 후 30분 안에 반드시 반영’은 다르다. API 계약에서 갱신 지연·기관별 조회 범위·호출 제한을 확인하기 전에는 전자를 서비스 동작으로 설명한다.

권장 문구:

> 30분 주기로 조회하며 기관 사정에 따라 반영이 지연될 수 있습니다.

재시도와 앱 실행 시 조회가 겹쳐도 거래·취소·알림이 중복 생성되지 않아야 한다. BullMQ 공식 문서 역시 재시도 여부와 관계없이 최종 결과가 같도록 작업을 설계하는 원칙을 안내한다. [BullMQ: Idempotent jobs](https://docs.bullmq.io/patterns/idempotent-jobs)

### 9.2 알림 정책

- 하루 최대 3건이 푸시만의 제한인지 이메일과 합산한 제한인지 확정한다.
- 방해 금지 중 발생한 알림의 발송 시각과 묶음 기준을 정한다.
- 이미 납부한 회차의 대기 중 알림을 취소한다.
- 예산 80%·100% 알림의 재발송 조건과 예산 수정·환불 후 처리를 정한다.
- 잠금 화면에서 금액·가맹점 등 민감한 내용의 노출 옵션을 검토한다.
- 푸시 권한 거부·미지원 상태에서도 앱 내 알림을 확인할 수 있게 한다.

iOS·iPadOS 웹 푸시에서는 홈 화면에 추가한 웹 앱과 사용자 동작에 따른 권한 요청 조건을 안내해야 한다. [WebKit: Web Push for Web Apps on iOS and iPadOS](https://webkit.org/blog/13878/)

### 9.3 데이터 관리

- 연결 해제 시 기존 거래 보존 여부.
- 사용자별 데이터 접근 제한.
- 회원 탈퇴·내보내기·삭제의 범위.
- 인증정보와 민감한 거래 정보의 로그 노출 방지.
- 백업·복구 기준과 복구 후 재동기화의 중복 방지.

## 10. 1차 출시 범위 재정의

수동·CSV 우선 출시는 적절한 방향이다. 다만 첫 화면의 주 동작이 아직 제공하지 않는 ‘카드 연결’이면 실제 출시 범위와 맞지 않는다.

1차 출시에서는 다음 흐름이 끊기지 않아야 한다.

```text
첫 진입
→ 수동 입력 또는 CSV 미리보기
→ 거래 저장
→ 합계 확인
→ 고정지출 등록
→ 납부 연결·수정
→ 예산 확인
```

| 시점 | 우선 확정·구현할 내용 |
| --- | --- |
| 구현 전 확정 | 소비 집계 기준, 예산 공식, 과거 월 수정 정책, 고정지출 적용 시작점 |
| 1차 필수 | 수동·CSV, 재업로드 중복 방지, 수정·삭제, 고정지출 회차와 납부 연결, 계산 근거 표시 |
| 자동 연동 전 필수 | 거래 갱신·취소, 사용자 수정 보호, 재수집·복구, 데이터 누락 표시 |
| 이후 확장 | 실제 현금 잔액 예측, 할부 청구 기준, 외화 확정 금액, 복잡한 반복 결제 |

보안과 사용자별 접근 제한은 해당 데이터 처리 기능을 제공하는 시점부터 적용한다.
